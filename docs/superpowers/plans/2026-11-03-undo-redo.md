# Undo, Redo, Start Over and Try Again Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Players can undo and redo moves, start the current board over, and replay a solved board. History survives a reload, within storage limits.

**Architecture:** A pure `History` holds the start snapshot plus undo and redo stacks of `{ snapshot, moves }` entries. `Session` owns one `History`. It captures the board at each grab, records it when the grab turns into a move, and swaps its engine for a restored snapshot on undo, redo or Start Over. Saved games move to record version 2, which adds the start state, the 10 nearest undo and redo entries (coordinates rounded) and counters. Version 1 still loads. `app.ts` wires up the floating Undo/Redo buttons, a Start over bar button with a confirmation dialog, Try again in the solved overlay, and the analytics.

**Tech Stack:** TypeScript, Vite, Vitest (`npm test`), Playwright (`npm run e2e`), oxlint (`npm run lint`). Run npm through fnm (`/Users/bot/homebrew/bin/fnm exec npm …`, Node 22 from `.nvmrc`).

**Spec:** `docs/superpowers/specs/2026-11-03-undo-redo-design.md`

## Global Constraints

- Undo/redo jump instantly to a stored state: no animation.
- The move counter takes the restored entry's `moves` value. Start Over sets it to 0.
- Undo, Redo and Start Over do nothing while an end is held. Undo and Redo also do nothing once the puzzle is solved.
- Undo or Redo tapped while a dropped end is still flying or landing waits until every end is seated, then happens.
- Making a move clears the redo stack. Start Over clears both stacks and cannot be undone.
- Storage keeps up to 10 undo and up to 10 redo entries, the ones nearest the current position. In memory both stacks are unbounded.
- The saved-game JSON is capped at 1,000,000 characters (`GAME_CHAR_CAP`). Entries are dropped in this order: the redo entry furthest ahead first, then the oldest undo entry. The same order applies when `setItem` throws. The current and start states are never dropped.
- Version-1 saved games must still load: no start state, empty history, counters 0. Never reject a real saved game (AGENTS.md).
- Start Over asks for confirmation unless the game is solved. Try Again never asks.
- Analytics: `puzzle-completed` gains `undos`, `redos`, `startOvers`, `replay`. New event `game-restarted { ropes, moves, ropesLeft, via: "start-over" | "try-again" }`. No per-undo events.
- Start Over and Try Again restart the play clock (`gameStartedAt`).
- American English in code. Add comments only where clearly worth their upkeep.

## Review Focus

1. Grabbing a second rope while the first dropped end is still flying merges the two moves into one undo step. The undo must restore the board from before both, with the counter down by 2. *(Task 2 test.)*
2. Undo tapped mid-flight must not be lost: it fires once the end lands, and Redo then returns the landed board. *(Task 2 test.)*
3. Tapping a disabled button, or tapping during a solved/held state, must change nothing. This covers rapid double taps on Undo with one entry left. *(Task 2 test.)*
4. A reload right after Start Over or Try Again must resume the restarted board with the counter at 0 and no undo history, not the pre-restart board. *(Task 5 e2e.)*
5. On a short, wide viewport the floating buttons must not cover any hole. *(Task 5 e2e.)*

### Task 2: Session undo, redo and Start Over

**Files:**
- Modify: `src/game/session.ts`
- Test: `tests/session.test.ts`

**Interfaces:**
- Consumes: `History`, `HistoryEntry` (Task 1); `toSnapshot`, `fromSnapshot` (`src/engine/snapshot.ts`).
- Produces (on `Session`):
  - `engine: Engine`, no longer `readonly`, because undo replaces it.
  - `readonly history: History`
  - `constructor(engine: Engine, history: History = new History(toSnapshot(engine)))`
  - `undos = 0; redos = 0; startOvers = 0; replay = false`
  - `undo(): boolean`, `redo(): boolean`: return `true` if done now or queued.
  - `startOver(): boolean`: return `true` if it reset the board.
  - `canUndo(): boolean`, `canRedo(): boolean`, `canStartOver(): boolean`
  - `queued: "undo" | "redo" | null`, public for tests.

Behavior:
- `grab`: before `E.grab`, store `before = E.endsSeated() ? { snapshot: toSnapshot(E), moves: this.moves } : null`. `grab` returns `false` while `queued !== null`.
- `release`: if the end moved to another hole, call `history.recordMove(before)`. Then clear `before`.
- `undo()`/`redo()`: return `false` if `won`, if `phase === "held"`, or if the relevant stack is empty (and nothing is queued). If `!E.endsSeated()`, set `queued` and return `true`. Otherwise jump now. `step()` runs the queued action at the end of a frame once `E.endsSeated()`.
- Jump: take `current = { snapshot: toSnapshot(E), moves }`, call `stepBack(current)` or `stepForward(current)`, then `engine = fromSnapshot(entry.snapshot)`, `moves = entry.moves`, clear `fades`, `revision++`, `settle()`, and increment `undos` or `redos`.
- `startOver()`: return `false` if `history.start === null` or `phase === "held"`. Otherwise jump to `history.start` with `moves = 0`, call `history.clear()` and clear `queued`. If `won`, set `won = false` and `replay = true`; else increment `startOvers`.
- `canUndo()` = `!won && phase !== "held" && history.canUndo()`. `canRedo()` likewise. `canStartOver()` = `history.start !== null && phase !== "held"`.

### Task 3: Saved-game record version 2

**Files:**
- Modify: `src/game/records.ts`
- Test: `tests/records.test.ts`

**Interfaces:**
- Consumes: `HistoryEntry` (Task 1).
- Produces:
  - `GAME_VERSION = 2`
  - `SavedGame` gains `start: EngineSnapshot | null; undo: HistoryEntry[]; redo: HistoryEntry[]; undos: number; redos: number; startOvers: number; replay: boolean`
  - `encodeSnapshot(s: EngineSnapshot, decimals?: number): SnapshotJson`. With `decimals`, every coordinate is rounded to that many decimals. Without it, the output is unchanged.
  - `export const HISTORY_DECIMALS = 2`
  - `export interface HistoryEntryJson { moves: number; snapshot: SnapshotJson }`
  - `encodeGame(g: SavedGame): GameJson`. It writes `start`, `undo` and `redo` with `HISTORY_DECIMALS`, and `snapshot` at full precision.
  - `decodeGame(v: unknown): SavedGame | null` accepts `v: 1`, mapping it to `start: null`, empty stacks, zero counters and `replay: false`, and `v: 2`. An undecodable history entry drops that entry, never the game. An undecodable `start` becomes `null`.
  - `writeText(store: KeyValueStore, key: string, text: string): boolean`. `writeRecord` delegates to it.
